# Software Design and Engineering

## CS 360 Inventory Management Android Application

The artifact selected for the Software Design and Engineering category is an Inventory Management Android application originally developed in CS 360: Mobile Architecture and Programming.

The application was enhanced during CS 499 to demonstrate growth in software design and engineering. Enhancements included inventory categories, searching by item name or category, configurable low-stock thresholds, stronger input validation, improvements to the inventory display and database upgrade process, and refactoring of the stock-status logic.

This section provides both the original artifact and the enhanced version so that the improvements made during the capstone can be reviewed.

## Enhancement Narrative

	The artifact I selected for the software design and engineering portion of my ePortfolio is my Inventory Management android application that I originally developed in CS 360: Mobile Architecture and Programming. The application was created as an Android Studio project using Java and SQLite. Its original purpose was to allow users to create an account, log in and manage inventory records. Users could add inventory items, view their quantities, increase or decrease quantities, delete items and access SMS permission settings. The application provided a functional foundation for inventory management, but there were opportunities to expand its functionality and improve the organization and reliability of the code.
	I selected this artifact because it demonstrates several areas of software development, including Android application development, user interface design, Java programming, database management, input processing and application logic. It also provided a good opportunity to demonstrate how an existing software application can be analyzed and improved rather than simply creating a new program. For the enhancement, I expanded the inventory management capabilities by adding categories to inventory records and allowing users to search inventory by either item name or category. I also replaced the original hard coded low stock value with a configurable threshold stored with each inventory item. The application can now determine whether an item is out of stock, low in stock, or in stock based on the item’s individual threshold.
	I also improved the reliability and maintainability of the application. Input validation was strengthened so that required inventory information must be provided, and quantity and threshold values are validated before being stored. Database constraints provide another layer of protection against invalid negative values. I refactored the stock status calculation into a separate method instead of keeping that logic directly inside the inventory display method. This reduces the responsibilities of the display method and makes the status logic easier to understand and maintain. I also improved the database upgrade process so that upgrading the schema adds the new category and threshold fields while preserving existing user and inventory records instead of deleting and recreating the database tables. Finally, the inventory interface was updated to accommodate the additional information and controls while maintaining access to features such as quantity updates and item deletion.
	The enhancement made progress toward the course outcomes I identified during Module One, particularly outcomes three, four and five. Outcome three is demonstrated through the design decisions involved in expanding the inventory data model and implementing threshold-based stock evaluation and search functionality. These changes required me to consider how inventory data should be stored, retrieved, evaluated and presented while maintaining the application’s existing functionality. Outcome four is demonstrated through my use of Java, Android Studio, SQLite, Android user-interface components and database queries to implement functionality that provides additional value to an inventory management application. The enhanced application provides users with more useful ways to organize, locate and evaluate their inventory.
	The enhancement also demonstrates progress toward outcome five by applying a stronger security and reliability mindset to user input and stored data. User provided inventory values are validated before being processed, database constraints help prevent invalid quantities and thresholds from being stored and the search functionality uses parameterized query values rather than constructing the search directly from user input. Reviewing the application also helped me recognize additional security concerns that could be addressed in future development, particularly the original application’s handling of user passwords. Password storage was outside the primary scope of this enhancement but identifying it as an area requiring stronger protection demonstrates the importance of considering security throughout the software development process rather than treating security as a separate feature.
	Enhancing this artifact taught me that improving existing software requires more than simply adding features. Changes to one part of an application can affect its database structure, application logic, user interface and existing functionality. For example, adding categories and low stock thresholds required changes to both the SQLite database and the activities that create and display inventory records. I also had to consider how existing data would be handled when the database structure changed. Replacing a destructive database upgrade with a migration approach reinforced the importance of preserving user data when software evolves.
	One of the challenges I encountered was fitting the additional inventory information and controls into the existing mobile interface. Adding category information created more columns than could comfortably fit on the screen, which initially caused the delete control to appear outside the visible area. I addressed this by making the inventory grid horizontally scrollable so that users could still access all of the information and controls. I also had to ensure that the new threshold logic worked correctly with the existing quantity update functionality and that search results updated without removing the application’s existing features. Testing each change individually helped me identify these issues while limiting the possibility of introducing errors into functionality that already worked.
