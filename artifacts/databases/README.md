# Databases

## CS 465 Travlr Getaways Application

The artifact selected for the Databases category is the Travlr Getaways full-stack web application originally developed in CS 465: Full Stack Development I.

The application uses the MEAN stack, including MongoDB, Express, Angular, and Node.js. MongoDB provides persistent storage, Mongoose models and schemas define the stored data, Express and Node.js provide the server-side application and API, and Angular provides the administrative single-page application.

During CS 499, I enhanced the database implementation by strengthening Mongoose validation, adding controlled trip filtering, improving database error handling, using findOne() for individual trip retrieval, enabling validation during update operations, and adding an index to support resort searches.

This section provides both the original artifact and the enhanced version so that the improvements made during the capstone can be reviewed.

## Enhancement Narrative

The artifact I selected for the databases portion of my ePortfolio is the Travlr Getaways full stack web application that I originally developed in CS 465: Full Stack Development I. The application was created using the MEAN stack, which includes MongoDB, Express, Angular and Node.js. MongoDB provides persistent storage for the application, while Mongoose models and schemas define the structure of the stored data. Express and Node.js provide the server-side application and API, while Angular provides the administrative single page application. The original application allowed trip information to be stored, retrieved, created and updated through the API and provided a strong foundation for demonstrating database development within a larger full stack application.

I selected this artifact because it demonstrates several areas of database and full stack development, including NoSQL database design, MongoDB, Mongoose schemas, database queries, API integration, data validation and authentication. It also provided an opportunity to demonstrate how an existing database implementation can be evaluated and improved rather than replacing the original application. For the enhancement, I strengthened the Mongoose trip schema by adding additional validation to the stored trip information. String values are trimmed, appropriate minimum and maximum lengths are enforced, and trip codes are normalized to uppercase. I also enabled validation during update operations so that the same rules used when creating a trip are applied when an existing record is modified.
  
I also expanded the application’s database querying capabilities. The original trip-list operation retrieved every trip using an empty MongoDB query. The enhanced version builds a controlled query based on supported parameters and allows trip records to be filtered by code, name or resort. The individual trip lookup was also changed to use findOne() because the operation is intended to retrieve a single trip. These changes provide more precise ways to retrieve data while maintaining the application’s original ability to return all trips when no filter is supplied.
  
The database error handling was also improved. Database operations now use exception handling so that unexpected errors can be logged internally while the client receives an appropriate response without unnecessary internal database information. Validation failures are handled separately from unexpected server errors, allowing invalid trip information to be rejected with a bad-request response. I tested the enhanced validation by attempting to create an invalid trip, which was rejected, and then creating a valid test trip, which was successfully stored. I also tested an invalid update to an existing trip and confirmed that the update was rejected by the schema validation.
  
Another part of the enhancement involved evaluating the database indexes. The original trip schema already contained indexes for the code and name fields. Because resort was added as one of the supported search criteria, I added an index to the resort field and verified through MongoDB Compass that the index was successfully created and used. The current database contains only a small number of trip records, so the test does not provide enough evidence to claim a measurable performance increase. Instead, the enhancement demonstrates how an index can be selected based on the application’s query requirements while avoiding unnecessary indexes.
  
The enhancement made progress toward the course outcomes I identified during Module One, particularly outcome three, four and five. Outcome three is demonstrated through the decisions involved in improving query construction, validation and indexing. These changes required me to consider how trip data should be stored and retrieved while also considering the tradeoffs involved in database indexing. Adding indexes can improve retrieval for frequently searched fields, but unnecessary indexes can also add storage and maintenance costs. Connecting the resort index to an actual search requirement provided a reason for the design decision rather than adding an index without a specific purpose.
  
Outcome four is demonstrated through my use of MongoDB, Mongoose, Express, Node.js and REST API operations to improve the existing application. The enhancement expanded the application’s database capabilities while maintaining its original functionality. Controlled queries provide more useful ways to retrieve trip information, stronger schema validation improves data integrity, and the additional index supports one of the application’s new search options. These changes demonstrate the use of databases and full stack development tools to provide additional value to the original solution.
  
The enhancement also demonstrates progress toward outcome five by applying a stronger security mindset to database interactions. The enhanced application limits filtering to supported query parameters rather than directly using arbitrary client input to construct database queries. Schema validation provides additional protection against invalid information being stored, while improved error handling prevents internal database errors from being unnecessarily returned to clients. The application also maintains its existing authentication requirements for protected operations such as creating and updating trip records. These changes are consistent with my original outcome coverage plan, so I do not currently need to change the outcomes selected for this artifact.
  
Enhancing this artifact taught me that database development involves more than storing and retrieving information. The structure of the data, validation rules, queries, indexes, API behavior and error handling all affect the reliability of the application. One important lesson was that adding validation to a schema is not enough by itself. I also needed to make sure that the validation rules were applied during update operations. Testing both invalid create and update requests helped confirm that the rules were being enforced throughout the application.
  
I also gained a better understanding of database indexing. The original application already contained indexes on two fields, so adding additional indexes without considering how the application searches its data would not necessarily improve the design. Connecting the new resort index to the resort filtering capability helped me understand how indexing decisions should be based on actual query requirements. I also learned that performance results need to be interpreted carefully. Because the Travlr database contains only a small number of records, it would not be appropriate to use this test to conclude that the new index produces a measurable improvement in query speed.
  
One challenge I encountered was setting up and testing the full stack application on a different computer. I had just switched to a new laptop and the project required the Node.js and Angular dependencies, MongoDB service, original trip data and authentication to be configured before the enhanced database functionality could be tested completely. Once the environment was working, I tested the code, name and resort filters individually and tested both valid and invalid database operations. Working through these issues reinforced how the database is connected to the other components of a full stack application and how changes need to be tested without disrupting existing functionality. Overall, the enhancement strengthened the original Travlr Getaways application while expanding my understanding of database validation, controlled queries, indexing, error handling and secure data management.
